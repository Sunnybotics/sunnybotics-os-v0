# SunnyboticsOS — Machine Layer

A hardware-agnostic machine layer for robot fleets, plus an adapter that exposes
every machine to any consuming system over plain REST/JSON. Machines describe
themselves through one common interface — what they are, how they are doing, and
what they can be asked to do — and work is dispatched to them by *capability*
rather than by name. The consuming system never learns that a particular robot
exists, never learns its model, and never speaks ROS 2. It sends an HTTP request
saying "something that can do CLEANING", and gets back a mission it can follow to
a terminal state.

This repository contains the machine-side half: the interface definitions, two
simulated rovers that implement them, and the adapter that bridges ROS 2 to HTTP.

> **Every machine in this repository is simulated.** There is no robot attached.
> Battery, position, health and mission timing are generated by
> `machine_node.py`, and every machine object served over HTTP carries
> `"simulated": true`. The *interface* is not simulated — the messages, the
> action, the state machine and the REST contract are real, and a driver for
> physical hardware replaces exactly one file. See
> [What is simulated](#what-is-simulated-and-what-is-not).

## The contract

Two definitions in `src/sunnybotics_cmi/` are the real output of this project.
Everything else is an implementation of them.

### `MachineState.msg`

Published by every machine on `/machines/<machine_id>/state` at **1 Hz**. This is
the complete observable state of one machine, whatever kind of machine it is.

Enum fields are integers on the wire and **readable strings in JSON**. Both are
listed below; the adapter does the translation and the OS only ever sees strings.

| Field | Type | Meaning |
|---|---|---|
| `interface_version` | `string` | Version of this contract the machine speaks. Currently `"0.1.0"`. Lets a partly-upgraded fleet keep working instead of needing a flag-day. |
| `seq` | `uint32` | Per-machine publish counter, +1 per message. A gap means messages were dropped — information the timestamp alone cannot give you. |
| `machine_id` | `string` | Unique across the fleet, e.g. `"rover_01"`. |
| `machine_type` | `string` | Model or class, e.g. `"cleaning_rover"`. **Informational only** — nothing in the system routes on it. |
| `capabilities` | `string[]` | What this machine can be asked to do, e.g. `["cleaning"]`. Free-form strings, compared case-insensitively; the only thing missions are matched against. |
| `state` | `uint8` | Mission lifecycle. See values below. |
| `health` | `uint8` | Condition, independent of `state`. See values below. |
| `operating_mode` | `uint8` | Autonomy level. See values below. |
| `connection_status` | `uint8` | Link status, independent of `state`. See values below. |
| `has_battery` | `bool` | Whether `battery_percent` means anything. |
| `battery_percent` | `float32` | 0.0–100.0. **`null` in JSON when `has_battery` is false**, never `0.0`. |
| `has_location` | `bool` | Whether the coordinate fields mean anything. |
| `frame_id` | `string` | Frame the coordinates are in, e.g. `"site_A_local"`. Not necessarily geographic. |
| `latitude` | `float64` | Northing. In `site_A_local` this carries local **Y metres**. |
| `longitude` | `float64` | Easting. In `site_A_local` this carries local **X metres**. |
| `current_mission_id` | `string` | Mission currently held. Empty string on the wire, **`null` in JSON**, when idle. |
| `active_errors` | `string[]` | Active error codes, e.g. `["OBSTACLE_DETECTED"]`. Empty when healthy. |
| `active_error_severities` | `uint8[]` | Parallel to `active_errors` — index *i* is the severity of error *i*. |
| `stamp` | `builtin_interfaces/Time` | When the machine produced this state. **ISO 8601 UTC in JSON.** |

#### Enum values

| Field | Int | JSON string | Meaning |
|---|---|---|---|
| `state` | 0 | `AVAILABLE` | Idle and able to accept a mission. |
| | 1 | `ASSIGNED` | Mission accepted, work not yet started. |
| | 2 | `RUNNING` | Actively executing. |
| | 3 | `COMPLETED` | Finished successfully. Held briefly, then returns to `AVAILABLE`. |
| | 4 | `EXCEPTION` | Finished with a failure. Held briefly, then returns to `AVAILABLE`. |
| `health` | 0 | `OK` | Nominal. |
| | 1 | `DEGRADED` | Impaired but still working. **Does not block missions.** |
| | 2 | `FAULT` | Faulted. |
| `operating_mode` | 0 | `MANUAL` | Under direct manual control. |
| | 1 | `TELEOP` | Remotely operated. |
| | 2 | `SEMI_AUTO` | Autonomous with supervision. |
| | 3 | `AUTOMATIC` | Fully autonomous. Both rovers here report this. |
| `connection_status` | 0 | `ONLINE` | Reachable. |
| | 1 | `OFFLINE` | Machine reports itself as out of service. |
| | 2 | `CONNECTION_BROKEN` | Not heard from. **Set by the adapter**, not the machine — see below. |
| `active_error_severities` | 0 | `WARNING` | Non-fatal. |
| | 1 | `FATAL` | Fatal to the current mission. |

The constants are named `SEVERITY_WARNING` / `SEVERITY_FATAL` in the `.msg`; the
`SEVERITY_` prefix is dropped in JSON.

**`CONNECTION_BROKEN` is inferred, not reported.** A machine whose link has
genuinely failed cannot transmit a message saying so. If no heartbeat arrives for
more than `stale_after_sec` (default **5 s**, i.e. five missed ticks), the adapter
overrides `connection_status` to `CONNECTION_BROKEN` on its own. Every other field
is passed through as last heard, so you can still see where the machine was and
what it was doing when it went quiet. Watch `seconds_since_last_message` for how
stale that is.

### `Mission.action`

Served by every machine at `/machines/<machine_id>/execute_mission`.

**Goal** — what gets dispatched:

| Field | Type | Meaning |
|---|---|---|
| `mission_id` | `string` | Assigned by the adapter. Echoed back in `MachineState.current_mission_id`, so fleet view and mission view join without guessing. |
| `capability_required` | `string` | Matched against `MachineState.capabilities`. Sent even though the adapter already matched on it, so the machine can refuse work it cannot do. |
| `objective` | `string` | Human-readable intent, e.g. `"Clean aisle 3"`. |
| `parameters_json` | `string` | A JSON object, as a string. Everything type-specific goes here. |

**Result** — exactly one, guaranteed, per accepted mission:

| Field | Type | Meaning |
|---|---|---|
| `result_state` | `uint8` | `RESULT_COMPLETED` (0) or `RESULT_EXCEPTION` (1). In JSON: `"COMPLETED"` / `"EXCEPTION"`. |
| `error_code` | `string` | Machine-readable failure code. Empty on success (`null` in JSON). |
| `message` | `string` | Human-readable summary. |
| `result_json` | `string` | A JSON object, as a string. Parsed into an object by the adapter. |

**Feedback** — emitted repeatedly while running:

| Field | Type | Meaning |
|---|---|---|
| `progress_percent` | `uint8` | 0–100. |
| `status_message` | `string` | What the machine is doing right now. |

#### Error codes currently produced

| Code | Severity | Raised when |
|---|---|---|
| `OBSTACLE_DETECTED` | `FATAL` | A mission is blocked and aborted. |
| `MISSION_CANCELLED` | — | The mission was cancelled while running. |
| `DISPATCH_TIMEOUT` | — | The machine never acknowledged the goal. Adapter-generated. |
| `GOAL_REJECTED` | — | The machine refused the goal. Adapter-generated. |
| `SIM_SENSOR_GLITCH` | `WARNING` | Simulation only — a transient health blip. |

## Design decisions and why

**`state` and `health` are separate fields.** A machine can be `RUNNING` while
`DEGRADED`, and perfectly `OK` while sitting idle. Collapsing them into one status
loses the difference between *not working* and *not well* — and that difference
decides whether you dispatch to it or send someone to look at it. Low battery
degrades a machine here; it does not stop it accepting missions.

**`connection_status` is separate from `state`.** Without it, a machine that went
silent keeps reporting its last known `state` forever. A silent machine still
reading `AVAILABLE` would have missions dispatched into a void. Keeping the link
status independent means the OS can distinguish "idle" from "we have no idea",
which are the same value in `state` but opposite in consequence. This is visible
in the API: a stale machine returns `"state": "AVAILABLE"` *and*
`"connection_status": "CONNECTION_BROKEN"` together, and the adapter refuses to
dispatch to it.

**Capabilities are flat strings, not an enum.** Adding a capability must not
require a schema change, a regenerated message, a rebuild of the OS, or a
coordinated redeploy across the fleet. A machine advertising `"lifting"` is
matchable the moment it starts, by a system that has never heard the word.

They are compared **case-insensitively**, and lowercase is the convention. This
matters more than it sounds: a capability is a bare string on both sides of the
interface, so a case mismatch raises nothing at all — the machine is simply
never selected, and the fleet looks idle for no visible reason. Folding case
turns the convention into a preference rather than a trap.

**`machine_type` exists but is never routed on.** It is there for operators and
dashboards. Nothing in the matching path reads it — which is what stops
machine-specific knowledge leaking upward. Both machines in this repository are
rovers, so type could not be doing the routing even if something wanted it to.

**A mission is an action, not a topic or a service.** This is the load-bearing
choice. An action gives four things a topic or a service cannot give together:
it is *accepted or rejected up front* with a reason, it *reports progress
correlated to a specific mission*, it can be *cancelled*, and it produces
*exactly one guaranteed terminal result*. A service call would block for the whole
mission; a topic would give no acknowledgement and no result at all.

**`has_location` guards `latitude`/`longitude`, `has_battery` guards
`battery_percent`.** Otherwise `0, 0` is ambiguous between "sitting exactly on
the origin" and "no idea where this is", and `0.0` battery is ambiguous between
"flat" and "not applicable". The adapter honours the guards by emitting `null`
rather than passing a meaningless number through.

**Enum integers become strings at the HTTP boundary.** `"state": 2` in a log line
tells an operator nothing; `"state": "RUNNING"` tells them everything. The
translation tables are keyed off the generated constants, so renumbering a
constant in the `.msg` propagates automatically and renaming one fails loudly at
start-up rather than silently emitting the wrong string.

### `POST /api/v0/missions` — dispatch work

The request names a **capability**, never a machine. The adapter picks one.

```console
$ curl -s -X POST http://127.0.0.1:8001/api/v0/missions \
    -H 'Content-Type: application/json' \
    -d '{"capability_required":"cleaning","objective":"Clean aisle 3","parameters":{"target_x":18.0,"target_y":9.0}}'
```

Request body:

| Field | Type | Required | Meaning |
|---|---|---|---|
| `capability_required` | `string` | yes | Must be non-empty. Matched against `capabilities`. |
| `objective` | `string` | no (default `""`) | Human-readable intent. |
| `parameters` | `object` | no (default `{}`) | Forwarded verbatim as `parameters_json`. |
| `mission_id` | `string` | no | The id the caller has already issued. See below. |

**Send `mission_id` if you have one.** A consuming system usually issues its own
id before dispatching. Supply it here and it is used as-is: the response echoes
it, and every progress report and result comes back under it.

Omit it and the adapter generates one -- which means the mission has *two*
identities, and the caller has to keep a mapping between the id it issued and
the id it got back. Reports then arrive under an id the caller does not
recognise. The usual symptom is a mission that appears stuck at its initial
state forever while a duplicate record quietly completes beside it.

A `mission_id` that has already been used returns `409` with
`reason: "mission_id_already_used"` rather than silently overwriting the
earlier mission.

**201 — dispatched:**

```json
{
  "mission_id": "m-0fa4380170dd",
  "assigned_machine_id": "rover_01",
  "state": "ASSIGNED"
}
```

Selection policy: any machine that advertises the capability, is `AVAILABLE`,
reports `ONLINE`, is not stale, and has at least `min_battery_percent` battery
(10% by default). Ties break on highest battery, so repeated missions spread
across a fleet rather than hammering the first machine. A mains-powered
machine (`has_battery: false`) sorts ahead of every battery-powered one, since
it has no battery constraint at all.

A machine under the battery minimum is filtered out here, at the adapter, and
also refuses the goal itself if a mission reaches it anyway — the same
defence-in-depth as the capability check. Below is why: a machine that accepts
a mission it cannot finish is worse than one that refuses it, and a `409`
naming the reason is more useful than a mission that quietly never returns.

Parameters understood by the simulated machines:

| Key | Type | Effect |
|---|---|---|
| `simulate_failure` | `bool` | Abort at 60% with `OBSTACLE_DETECTED`. |
| `target_x`, `target_y` | `float` | Where the machine drives to while `RUNNING`. Also accepts `{"target": {"x": …, "y": …}}`. |

Anything else is forwarded and ignored.

#### `409` — nothing can take the work

Three distinct `reason` values, and they call for different responses:

**`no_machine_with_capability`** — nothing in the fleet can *ever* do this. Do
not retry; this is a configuration or planning problem.

```json
{
  "detail": {
    "reason": "no_machine_with_capability",
    "capability_required": "welding",
    "machines_with_capability": [],
    "why_not_selected": {}
  }
}
```

**`no_available_machine`** — capable machines exist but none can take it right
now. Retry shortly. `why_not_selected` says why, per machine:

```json
{
  "detail": {
    "reason": "no_available_machine",
    "capability_required": "cleaning",
    "machines_with_capability": ["rover_01"],
    "why_not_selected": { "rover_01": "not AVAILABLE" }
  }
}
```

```json
{
  "detail": {
    "reason": "no_available_machine",
    "capability_required": "inspection",
    "machines_with_capability": ["rover_02"],
    "why_not_selected": { "rover_02": "CONNECTION_BROKEN (no heartbeat)" }
  }
}
```

**`machine_rejected_goal`** — the adapter selected a machine, but the machine
itself refused. Retry shortly.

```json
{
  "detail": {
    "reason": "machine_rejected_goal",
    "mission_id": "m-f4c2ad7a865a",
    "assigned_machine_id": "rover_01"
  }
}
```

This happens because the fleet view is a 1 Hz snapshot. Dispatch two missions
within the same heartbeat window and the adapter still believes the machine is
free; the machine, which knows better, rejects the second. **Treat
`machine_rejected_goal` and `no_available_machine` the same way** — both mean
"try again in a moment". The machine re-checking for itself is the interface
working correctly, not a fault.

#### `503` / `504` — transport problems

| Status | `reason` | Meaning |
|---|---|---|
| 503 | `action_server_unreachable` | The machine publishes state but its mission server did not answer within 5 s. |
| 503 | `action_client_not_ready` | Discovery was mid-flight. Retry immediately. |
| 504 | `goal_not_acknowledged` | The goal was sent but never acknowledged. The mission is recorded as `EXCEPTION` with `DISPATCH_TIMEOUT`. |

### `GET /api/v0/missions/{mission_id}` — follow a mission

Exactly six fields, always.

| Field | Type | Meaning |
|---|---|---|
| `mission_id` | `string` | As returned by `POST /api/v0/missions`. |
| `assigned_machine_id` | `string` | Which machine took it. |
| `state` | `string` | `ASSIGNED`, `RUNNING`, `COMPLETED`, `EXCEPTION`, `REJECTED`, `CANCELED`. |
| `progress_percent` | `int` | 0–100. |
| `status_message` | `string` | Latest human-readable status. |
| `result` | `object \| null` | `null` until terminal. |

The first four states mirror the `MachineState` vocabulary. `REJECTED` and
`CANCELED` have no machine equivalent — they describe what happened to the
*request*, not to the machine.

**In progress:**

```json
{
  "mission_id": "m-0fa4380170dd",
  "assigned_machine_id": "rover_01",
  "state": "RUNNING",
  "progress_percent": 40,
  "status_message": "Clean aisle 3 -- 40% (step 4/10)",
  "result": null
}
```

**Completed:**

```json
{
  "mission_id": "m-0fa4380170dd",
  "assigned_machine_id": "rover_01",
  "state": "COMPLETED",
  "progress_percent": 100,
  "status_message": "rover_01 completed m-0fa4380170dd: Clean aisle 3",
  "result": {
    "result_state": "COMPLETED",
    "error_code": null,
    "message": "rover_01 completed m-0fa4380170dd: Clean aisle 3",
    "result_json": {
      "simulated": true,
      "elapsed_sec": 6.01,
      "final_position": { "frame_id": "site_A_local", "x": 15.152, "y": 7.932 }
    }
  }
}
```

**Failed:**

```json
{
  "mission_id": "m-e8f71e8f7b7f",
  "assigned_machine_id": "rover_01",
  "state": "EXCEPTION",
  "progress_percent": 50,
  "status_message": "Simulated obstacle blocked rover_01 at 60% of m-e8f71e8f7b7f",
  "result": {
    "result_state": "EXCEPTION",
    "error_code": "OBSTACLE_DETECTED",
    "message": "Simulated obstacle blocked rover_01 at 60% of m-e8f71e8f7b7f",
    "result_json": {
      "failed_at_percent": 60,
      "simulated": true,
      "elapsed_sec": 3.0
    }
  }
}
```

Note `progress_percent` is 50 while the failure reports 60% — feedback is emitted
at the *start* of each step and the abort fires mid-step. The mission record keeps
the last progress actually reported.

**404 — unknown mission:**

```json
{ "detail": { "reason": "unknown_mission", "mission_id": "m-000000000000" } }
```

#### Polling and lifecycle

Mission records **outlive the machine's view of the work**. A machine holds
`COMPLETED` or `EXCEPTION` for about 3 seconds — long enough for a polling
consumer to observe it over a 1 Hz feed — then returns to `AVAILABLE` and clears
`current_mission_id`. The mission keeps its terminal state and result
indefinitely. Poll `GET /api/v0/missions/{id}`, not the machine, to find out how a
mission ended.

Mission history is **in memory only** and is lost when the adapter restarts.

## Architecture

Three processes. Only one of them knows ROS 2 exists.

```
   OS / Mission Engine  (any language, any host)
            │
            │  HTTP + JSON only.  No ROS 2 client, no ROS 2 install,
            │  no message definitions, no shared library.
            ▼
   ┌───────────────────────────────────────────────┐
   │  adapter                    one process       │
   │                                               │
   │   FastAPI          (main thread, sync handlers)│
   │            ▲                                  │
   │            │  threading.Lock                  │
   │            ▼                                  │
   │   rclpy executor   (background daemon thread) │
   └───────────────────────────────────────────────┘
            │                              ▲
            │ Mission action goal          │ MachineState @ 1 Hz
            ▼                              │
   ┌────────────────────┐        ┌────────────────────┐
   │ rover_01           │        │ rover_02           │
   │ cleaning_rover     │        │ inspection_rover   │
   │ ["cleaning"]       │        │ ["inspection"]     │
   └────────────────────┘        └────────────────────┘
        one node class, instantiated twice
```

**The machines** each publish their state once a second and run a mission action
server. They accept or refuse work, report progress, and end in one terminal
outcome.

**The adapter** listens for `/machines/*/state` topics, keeps the latest state of
every machine it can hear, matches incoming missions to a capable machine,
dispatches the goal, and tracks feedback and results. It holds the only ROS 2
dependency in the system.

**The consumer** speaks HTTP. That is the whole integration surface.

The adapter runs two runtimes in one process because neither will host the other:
`rclpy` needs a synchronous spin loop, FastAPI needs an asyncio one. The ROS
executor gets a daemon thread, uvicorn keeps the main thread, and shared state
sits behind a lock. The HTTP handlers are deliberately synchronous (`def`, not
`async def`) so FastAPI runs them in its worker threadpool, where blocking on that
lock or on an action server is correct — written as `async def` the same code
would stall the event loop for every other request.

## What is simulated, and what is not

Be clear about this before building on it.

**Simulated — every number is invented:**

| Field | Behaviour |
|---|---|
| `seq` | +1 per publish |
| `battery_percent` | −0.05/tick while `RUNNING`, −0.01/tick idle; never goes below 0 |
| `health` | `OK` above 20% · `DEGRADED` 5–20% · `FAULT` below 5%, at 0%, or during a fault blip; a battery-caused `FAULT` never clears itself |
| `active_errors` (battery) | `BATTERY_LOW` below 20% · `BATTERY_CRITICAL` below 5% · `BATTERY_DEPLETED` at 0% |
| New missions | Refused below a 10% battery minimum, so a machine is never sent out on a mission it cannot finish |
| At 0% battery | One last heartbeat, then the machine stops publishing — a real flat battery does not politely announce itself. Any mission already running aborts with `BATTERY_DEPLETED` first. The adapter's staleness check is what turns the silence into `OFFLINE` |
| `latitude` / `longitude` | Local Y/X metres, easing 25% of the remaining distance toward the mission target each tick |
| `connection_status` | `ONLINE` by default, changeable at runtime for testing |
| `active_errors` | Also carries `OBSTACLE_DETECTED`, `MISSION_CANCELLED`, or `SIM_SENSOR_GLITCH` when applicable |
| Feedback progress | 0→100 over a step count scaled to distance to the target (12–45 steps, 1 step ≈ 1 m), `mission_step_sec` apart |
| Mission duration | Proportional to distance to the target — roughly 7–27 s at the default 0.6 s/step, not related to any real task's actual duration |

**Real — the contract and the state machine:**

- the `MachineState` message and its 1 Hz publication
- the `Mission` action: accept/reject, progress, cancellation, one terminal result
- the lifecycle `AVAILABLE → ASSIGNED → RUNNING → COMPLETED | EXCEPTION → AVAILABLE`
- capability matching and everything the REST layer does
- `CONNECTION_BROKEN` inference from missing heartbeats

Static per machine, set once and never rewritten: `machine_id`, `machine_type`,
`capabilities`, `operating_mode`, `interface_version`.

Driven by the mission workflow and never faked separately: `state`,
`current_mission_id`, and all `Result` fields. This separation is deliberate —
if the simulation could write `state`, the published state could disagree with
what actually happened.

**A real robot driver deletes the simulated half, keeps the contract half, and
nothing else in the system changes.** Not the adapter, not the REST API, not the
consumer. That is the property this component exists to provide.

### Poking the simulation at runtime

```bash
# Machine reports itself out of service; it also refuses new missions.
ros2 param set /rover_01 sim_connection_status offline

# Link dies: the machine stops publishing entirely, and the adapter has to
# notice the silence itself, reporting CONNECTION_BROKEN after 5 s.
ros2 param set /rover_01 sim_connection_status connection_broken

ros2 param set /rover_01 sim_connection_status online

# Start with a low battery to reach DEGRADED immediately (must be under 20%).
ros2 run sunnybotics_machines rover_01 --ros-args -p initial_battery_percent:=15.0

# Start under the 10% mission minimum: new goals are refused on sight.
ros2 run sunnybotics_machines rover_01 --ros-args -p initial_battery_percent:=8.0

# Start dead: one heartbeat, then silence. The adapter reports it OFFLINE
# once stale_after_sec has passed with nothing heard.
ros2 run sunnybotics_machines rover_01 --ros-args -p initial_battery_percent:=0.0
```

Also settable: `fault_probability`, `mission_steps` (0 = derive from distance
to the target, the default; a positive value pins every mission to that many
steps regardless of distance), `mission_step_sec`, `terminal_state_hold_sec`,
`has_battery`, `start_x`, `start_y`. On the adapter: `stale_after_sec`,
`discovery_period_sec`, `action_server_timeout_sec`, `min_battery_percent`.

## Running it

### Prerequisites

- **Ubuntu 24.04** (Noble). On Windows, WSL2 works.
- **ROS 2 Jazzy Jalisco** — `ros-jazzy-desktop` or `ros-jazzy-ros-base` (base is
  enough; nothing here needs RViz or Gazebo)
- **Python 3.12** with `fastapi`, `uvicorn`, `pydantic`

Install ROS 2 Jazzy by following the
[official Jazzy install guide](https://docs.ros.org/en/jazzy/Installation/Ubuntu-Install-Debs.html),
then:

```bash
sudo apt install -y ros-dev-tools python3-fastapi python3-uvicorn python3-pydantic
```

> Install the Python packages with **apt, not pip**. Ubuntu 24.04 marks the
> system interpreter as externally managed (PEP 668), and `rclpy` lives only in
> that interpreter — so the web framework has to live there too. A virtualenv
> works only if created with `--system-site-packages`, or `rclpy` disappears.
> Note that apt ships pydantic v1; the code is compatible with v1 and v2.

### Build

```bash
git clone <this-repo>
cd <repo>/machine-layer
source /opt/ros/jazzy/setup.bash
colcon build
source install/setup.bash
```

`colcon build` must run from `machine-layer/`, not from the repository root —
that directory is the workspace, and `build/`, `install/` and `log/` are created
inside it.

Confirm the interfaces generated:

```bash
ros2 interface show sunnybotics_cmi/msg/MachineState
ros2 interface show sunnybotics_cmi/action/Mission
```

> Do not run `colcon build` from a shell with `set -u` active. ROS 2's
> `setup.bash` references unset variables and will abort.

### Run

Three terminals. Each needs the workspace sourced:

```bash
source /opt/ros/jazzy/setup.bash && source install/setup.bash
```

Keeping ROS traffic on loopback avoids slow multicast discovery on virtualised
network interfaces:

```bash
export ROS_DOMAIN_ID=42
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
```

**Terminal 1 — the machines:**

```bash
ros2 launch sunnybotics_machines machines.launch.py
```

**Terminal 2 — the adapter:**

```bash
ros2 run sunnybotics_adapter adapter
```

Options: `--host` (default `127.0.0.1`), `--port` (default `8001`),
`--log-level`.

**Terminal 3 — the demo:**

```bash
python3 demo/demo.py
```

### Test suites

**`demo/demo.py`** exercises the chain end to end and exits non-zero if anything
fails, so it works as a smoke test as well as a demonstration:

1. **Golden run** — a `CLEANING` mission reaches `COMPLETED`
2. **Failure path** — the same mission with `simulate_failure: true` reaches
   `EXCEPTION` with `OBSTACLE_DETECTED`, driven purely by the request body with
   no code changed between runs
3. **Capability routing** — an `INSPECTION` mission lands on `rover_02` without
   anything naming `rover_02`
4. **No match** — an unadvertised capability is refused with 409 rather than
   dispatched into a void

```bash
python3 demo/demo.py --host 127.0.0.1 --port 8001
echo $?   # 0 if every scenario passed
```

The demo imports no ROS packages and does not need the workspace sourced. It
stands exactly where the consuming system stands.

## Pushing to the OS

By default the adapter is only a server: it holds fleet state and answers the
API above. That requires the consuming OS to reach *into* the machine network,
which in a real deployment means the robots must be publicly addressable or sat
behind a tunnel — and machines are normally the ones behind NAT.

So the adapter can also work the other way round, as a client that registers
itself and pushes. Point it at the OS and it does both:

```bash
ros2 run sunnybotics_adapter adapter --os-url http://<os-host>:9000
```

With no `--os-url` nothing is pushed and the behaviour is exactly as documented
above, so this costs nothing while the OS side does not exist yet.

Three calls are made, matching the OS-side contract:

| When | Call |
|---|---|
| First heartbeat from a machine | `POST /api/v0/machines/register` |
| Every heartbeat after that (1 Hz) | `PATCH /api/v0/machines/{machine_id}/status` |
| Mission progress and outcome | `POST /api/v0/missions/{mission_id}/report` |

**Registration**, sent once per machine on the first heartbeat — the first
moment a descriptor exists to register:

```json
{
  "machine_id": "rover_01",
  "machine_type": "cleaning_rover",
  "capabilities": ["cleaning"],
  "state": "AVAILABLE",
  "health": { "connected": true, "faults": [], "battery_pct": 98.7 },
  "location": { "x": -0.7362, "y": 17.0461, "frame_id": "site_A_local" },
  "current_mission_id": null
}
```

**Heartbeat**, once a second per machine. Here mid-mission, so `state` is
`RUNNING` and `current_mission_id` is set:

```json
{
  "state": "RUNNING",
  "health": { "connected": true, "faults": [], "battery_pct": 99.9 },
  "location": { "x": 6.0, "y": 4.5, "frame_id": "site_A_local" },
  "current_mission_id": "m-f9790e270c99"
}
```

**Mission reports**, as work progresses and when it ends:

```json
{
  "mission_id": "m-f9790e270c99",
  "status": "RUNNING",
  "detail": "Clean aisle 3 -- 10% (step 1/10)",
  "timestamp": "2026-09-02T15:45:07.534Z",
  "progress_percent": 10
}
```
```json
{
  "mission_id": "m-f14e3a882af6",
  "status": "EXCEPTION",
  "detail": "Simulated obstacle blocked rover_01 at 60% of m-f14e3a882af6",
  "timestamp": "2026-09-02T15:45:22.525Z"
}
```

### What the translation loses

The OS state vocabulary is `AVAILABLE / ASSIGNED / RUNNING / OFFLINE`, which is
smaller than `MachineState` carries, so mapping down to it drops two things.
Both are recorded in `translate.py` so the loss is visible rather than
discovered later:

- **Connectivity is folded into `state` as `OFFLINE`.** A machine that is
  `RUNNING` and then loses its link has to be reported `OFFLINE`, which
  overwrites the fact that a mission is still executing somewhere. Keeping the
  link status in its own field would preserve both answers.
- **There is no terminal machine state.** `COMPLETED` and `EXCEPTION` live on
  the mission, so a machine that has just finished is reported `AVAILABLE` and
  the outcome travels in the mission report instead.

`progress_percent` is sent on reports even though it is not in the OS contract:
a consumer cannot draw a progress bar from `RUNNING` then `COMPLETED` alone, and
an unrecognised key is cheap to ignore.

### Behaviour when the OS is down

Pushing never blocks the ROS side. Sends are queued and drained by one
background thread, so a slow or absent OS delays telemetry but can never stall
the executor — which would otherwise stop the machines being heard from at all.
Failures are logged and dropped, the queue is bounded, and a machine whose
registration failed is retried on its next heartbeat. `GET /` reports
`sent` / `failed` / `dropped` / `queued` so the state of the link is visible.

### Testing it without the OS

`tools/os_stub.py` is a test double for the receiving end — it accepts the three
calls, records them, and answers with the documented success shapes. It has no
database and no Mission Engine.

```bash
python3 tools/os_stub.py --port 9000
ros2 run sunnybotics_adapter adapter --os-url http://127.0.0.1:9000
curl -s http://127.0.0.1:9000/_captured | python3 -m json.tool
```

## Remote access

The adapter binds `127.0.0.1` by default, which means nothing outside the host
can reach it. To let a consumer on another network drive the fleet, bind all
interfaces and put a tunnel in front:

```bash
ros2 run sunnybotics_adapter adapter --host 0.0.0.0 --port 8001
```

Then expose port 8001 with whatever tunnel you use, for example:

```bash
ngrok http 8001
# or: cloudflared tunnel --url http://localhost:8001
```

Point the demo at the resulting URL:

```bash
python3 demo/demo.py --host <tunnel-host> --port 443
```

Things that will bite you:

- **`--host 0.0.0.0` is opt-in for a reason.** There is no authentication on this
  API. Anything that can reach the port can drive the robots. Do not bind all
  interfaces on an untrusted network, and prefer a tunnel with access control over
  an open port.
- **Free tunnel URLs rotate.** Most free tiers issue a new hostname every time the
  tunnel restarts, so the consumer's base URL is not stable. Re-share it after
  each restart, or use a reserved domain on a paid tier.
- **Free tunnels may inject a browser interstitial.** Some providers return an
  HTML warning page instead of your JSON for requests that look like they came
  from a browser. With ngrok, suppress it by sending
  `ngrok-skip-browser-warning: true` on every request:

  ```bash
  curl -s -H 'ngrok-skip-browser-warning: true' https://<subdomain>.ngrok-free.app/machines
  ```

  Whatever HTTP client the consumer uses needs to send that header too. Note that
  `demo/demo.py` does **not** send it — if your tunnel interstitials it, the demo
  will fail to parse the response.
- **Point the consumer at the tunnel host, not `localhost`.** The base URL is
  configured per client; this repository does not read it from the environment.

## Adding a new machine type

A new machine type is configuration, not code. This is the entire integration:

```python
# forklift_01.py
from sunnybotics_machines.machine_node import run_machine

run_machine(
    machine_id="forklift_01",
    machine_type="pallet_forklift",
    capabilities=["lifting", "inspection"],
    start_x=-5.0,
    start_y=8.0,
)
```

```bash
python3 forklift_01.py
```

**The adapter discovers machines by scanning for `/machines/<id>/state` topics
once a second.** There is no machine list anywhere in this repository. Starting
the process above is sufficient — no rebuild, no adapter restart, no
configuration change, and nothing on the consumer side to update.

This is verified, not asserted. With the fleet and adapter already running, a
`lifting` mission is refused with `no_machine_with_capability`. Start
`forklift_01`, and within one discovery tick `GET /api/v0/machines` lists it and the
identical `lifting` request is accepted and runs to `COMPLETED`. To add it
permanently, drop the file into `src/sunnybotics_machines/sunnybotics_machines/`,
add one line to `entry_points` in `setup.py`, and it becomes `ros2 run`-able.

Note that `forklift_01` advertises `inspection` alongside `lifting`, so it also
becomes a candidate for inspection work — capability matching, not identity,
decides.

## Scope limits

Known and deliberate. None of these are hidden behind a "TODO".

- **No WebSocket push.** `WS /ws/machines` is the documented next step but is not
  implemented; consumers poll. The consequence is visible in the API: the fleet
  view is a 1 Hz snapshot, so it can be up to a second behind the truth, which is
  what produces the `machine_rejected_goal` race described above. Everything push
  needs already exists — the adapter holds live state and sees every update — what
  is missing is a connection registry and a fan-out on change.
- **No authentication or authorisation.** Any client that can reach the port can
  dispatch missions, and the outbound push sends no credentials either.
  Acceptable on loopback, not acceptable anywhere else.
- **No persistence.** Mission history lives in memory and dies with the adapter
  process. Machine state is reconstructed from heartbeats within a second of
  restart; mission records are not recoverable.
- **No real navigation.** Movement is linear interpolation toward a target
  coordinate. There is no map, no path planning, no obstacle avoidance, and no
  physics.
- **Single site.** One coordinate frame (`site_A_local`) is assumed throughout.
  There is no multi-site addressing and no frame transformation.
- **No multi-machine coordination.** Missions are matched one at a time to one
  machine. There is no queuing, no task decomposition, no reservation, and no
  handling of missions that need two machines at once.
- **No cancellation from the REST API.** The `Mission` action supports
  cancellation and the machines implement it, but no endpoint exposes it yet.
